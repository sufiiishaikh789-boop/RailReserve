## 1. Introduction

### 1.1 Purpose
The purpose of this document is to present the complete, unambiguous, and verifiable Software Requirements Specification for the Team 11 Railway Reservation System. This document serves as the formal contractual baseline between the student developers, faculty evaluators, and system stakeholders for the B.Tech Computer Science & Engineering capstone mini-project.

### 1.2 Document Scope
This document specifies both functional and non-functional requirements for a fully operational, web-based demonstration Railway Reservation System.
- **In-Scope:** Train schedule search, route validation, station sequence ordering, class selection, passenger detail validation, atomic seat reservation, simulated multi-outcome payment processing, unique PNR e-ticket generation, booking lookup, waiting-list queuing, deterministic cancellation and refund calculation, waiting-list auto-promotion, and protected administrative inventory management.
- **Out-of-Scope (Academic Boundaries):** Live integration with Indian Railways / IRCTC production mainframes, processing real banking credentials or live monetary payments, collection of real government identity records (Aadhaar/PAN), and commercial production deployment.

### 1.3 Definitions, Acronyms, and Abbreviations
- **ACID:** Atomicity, Consistency, Isolation, Durability.
- **BVA:** Boundary Value Analysis.
- **CNF:** Confirmed (Seat allocated with Coach and Berth identifier).

- **WL:** Waiting List (Booking accepted when confirmed capacity is exhausted; queued for promotion).

## 2. General Description

### 2.1 Product Perspective
The Railway Reservation System is a self-contained, modern three-tier client-server application. It operates as an independent web application utilizing a Single Page Application (SPA) frontend developed in React and TypeScript, an Express.js application service layer, and a persistent SQLite relational database.

```
+-------------------------------------------------------------+
|                  Client Layer (Browser)                     |
|        React 18 + TypeScript + Vite + Tailwind CSS          |
+-------------------------------------------------------------+
                              |
                     REST API / JSON (HTTP)
                              v
+-------------------------------------------------------------+
|              Application Server Layer (Node.js)             |
|          Express Controller & Business Logic Services       |
+-------------------------------------------------------------+
                              |
                    SQL Driver / Transactions
                              v
+-------------------------------------------------------------+
|                     Data Storage Layer                      |
|                  SQLite Relational Database                 |
+-------------------------------------------------------------+
```

### 2.2 Product Functions
1. Search trains across source and destination stations on designated journey dates.
2. Filter and sort trains by departure time, travel duration, and fare.
3. Validate passenger information and enforce boundary rules.
4. Calculate detailed fare breakdowns including base fare, class multipliers, and reservation fees.
5. Allocate seats atomically using database locks to prevent overbooking.
6. Provide simulated payment processing with deterministic success, failure, and cancellation paths.
7. Issue digital e-tickets featuring unique PNRs, coach/berth details, or waiting-list status.
8. Manage waiting-list queues and auto-promote passengers when confirmed cancellations occur.
9. Process ticket cancellations and compute deterministic refunds according to cancellation time windows.
10. Provide an administrative portal for managing train inventories, schedules, and viewing audit logs.

### 2.3 User Classes and Characteristics
1. **Unregistered / General Passenger:** Searches train schedules, views fares and seat availability without requiring login.
2. **Booking Passenger:** Inputs personal details, commits reservations, simulates payment, receives e-tickets, and checks booking history.
3. **System Administrator:** Authorized personnel responsible for adding trains, modifying seat quotas, adjusting base fares, and auditing operations.

### 2.4 Operating Environment
- **Client Runtime:** Modern web browsers (Google Chrome 110+, Mozilla Firefox 110+, Microsoft Edge 110+, Safari 16+).
- **Server Runtime:** Node.js v20.x LTS or v24.x LTS running on Windows, macOS, or Linux.
- **Database Engine:** SQLite 3 (persisted via native `node:sqlite` or filesystem storage).

### 2.5 Design and Implementation Constraints
- **Concurrency Constraint:** The system must guarantee zero overbooking under simultaneous booking requests.
- **Security Constraint:** Simulated payment modules must explicitly reject real credit card numbers, PINs, or CVVs.
- **Architectural Constraint:** Clean separation between presentation, application services, and persistence layers.
- **Language Constraint:** TypeScript must be used across both frontend and backend to guarantee compile-time type safety.

### 2.6 Assumptions and Dependencies
- Demonstration train schedules and station distances are fictional but realistic representations of Indian Railways corridors (e.g., Bengaluru-Chennai, Bengaluru-Mysuru, Bengaluru-Hyderabad).
- Network latency between client and server in the local test environment is $< 20$ ms.

## 3. Functional Requirements (FR)

### 3.1 User Functions

#### FR-01: Train Search by Origin, Destination, and Travel Date
- **Description:** The system shall allow users to search for trains connecting a selected origin station and destination station on a specified journey date.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - Given a valid origin, destination, and future date within 120 days, when search is initiated, then the system returns all trains that call at both stations where `origin_stop_sequence < destination_stop_sequence`.
  - If no trains connect the pair, an informative message *"No direct trains found for the selected route"* is returned.

#### FR-02: Validation of Search Parameters
- **Description:** The system shall reject invalid, empty, or logically impossible search queries before executing backend queries.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - Selecting identical origin and destination stations displays an inline error: *"Source and Destination stations cannot be identical"*.
  - Selecting a past date displays an inline error: *"Journey date must be today or a future date"*.
  - Selecting a date beyond 120 days displays: *"Reservations open only up to 120 days in advance"*.

#### FR-03: Display Train Schedules, Classes, Fares, and Availability
- **Description:** For every matching train, the system shall display the train number, name, departure time, arrival time, travel duration, overnight flag, available travel classes (1A, 2A, 3A, SL, CC, 2S), calculated fares, and live seat availability.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - When seat count $> 0$, the system displays `AVAILABLE - <N>`.
  - When seat count $= 0$ and waiting list capacity remains, the system displays `WL - <Position>`.
  - When seat count $= 0$ and waiting list is exhausted, the system displays `REGRET / NOT AVAILABLE`.

#### FR-04: Filter and Sort Search Results
- **Description:** The user shall be able to filter search results by travel class (e.g., AC only, Sleeper only) and sort results by departure time, journey duration, or fare.
- **Priority:** Medium (Should Have).
- **Acceptance Criteria:**
  - Sorting by 'Fare: Low to High' immediately rearranges the list without losing selected station criteria.

#### FR-05: Train and Class Selection
- **Description:** The user shall select a specific train and travel class to proceed to passenger data entry.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - Selection persists the train ID, schedule ID, class code, and unit fare into the active booking session.

### 3.2 Passenger & Booking Logic

#### FR-06: Passenger Data Input and Validation
- **Description:** The system shall accept details for 1 to 6 passengers per booking, including full name, age, gender, and berth preference. Contact email and phone number are captured for ticket delivery.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - Names containing non-alphabetic characters (except spaces) are rejected.
  - Ages $< 1$ or $> 120$ are rejected with an explicit error.
  - Valid 10-digit mobile phone and RFC-5322 compliant email format are enforced.

#### FR-07: Fare Breakdown Calculation
- **Description:** The system shall calculate a transparent fare breakdown prior to payment commitment, showing: Base Fare $\times$ Passenger Count $+$ Reservation Fee $+$ Superfast Surcharge (if applicable) $=$ Total Payable Fare.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - The fare breakdown matches the sum of individual passenger quotas exactly.

#### FR-08: Pre-Allocation Availability Verification
- **Description:** Immediately before opening a payment transaction, the system shall perform a fresh verification of remaining seat inventory to prevent stale client read collisions.
- **Priority:** Critical (Must Have).
- **Acceptance Criteria:**
  - If seats were taken by another user during passenger entry, the user is alerted with the choice to book Waiting List or abort.

#### FR-09: Atomic Seat Allocation and Prevention of Overbooking
- **Description:** The system shall execute seat assignment inside a database transaction with serializable isolation (`BEGIN IMMEDIATE`).
- **Priority:** Critical (Must Have).
- **Acceptance Criteria:**
  - In a concurrent simulation of 20 simultaneous booking requests for a coach with 5 available seats, exactly 5 receive confirmed seats and the remaining 15 receive waiting-list or rejection without overbooking.

### 3.3 Payment & Ticketing Functions

#### FR-10: Simulated Payment Processing
- **Description:** The system shall provide an interactive payment simulation modal offering options to simulate: (1) Successful Payment, (2) Payment Failure (insufficient funds / decline), or (3) User Cancellation / Gateway Timeout.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - Selecting 'Simulate Success' updates booking state to `CONFIRMED` or `WAITING_LIST` and marks payment as `PAID`.
  - Selecting 'Simulate Failure' transitions booking state to `FAILED` and releases any temporarily held inventory back to the pool immediately.
  - Selecting 'Simulate Failure' MUST NEVER generate a valid paid e-ticket.

#### FR-11: Unique Booking Reference (PNR) Generation
- **Description:** Upon confirmed payment, the system shall generate a globally unique, 10-character alphanumeric PNR reference (e.g., `PNR-829104`).
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - PNR numbers are strictly unique across the database (enforced by a SQLite `UNIQUE` constraint).

#### FR-12: Digital E-Ticket Generation and Display
- **Description:** The system shall render an e-ticket displaying PNR, Train Number & Name, Origin & Destination, Departure & Arrival datetimes, Passenger list with coach/seat/berth assignments (or WL number), total fare paid, and a clear demonstration watermark.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - The ticket provides a clean, printable layout with a 'Print / Save as PDF' trigger.

#### FR-13: Booking History and PNR Status Lookup
- **Description:** Users shall be able to look up any booking by entering its PNR, or view all bookings associated with their contact email/phone number.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - Searching a valid PNR displays the live status (`CONFIRMED`, `WAITING_LIST`, or `CANCELLED`).
  - Search prevents cross-user modification by requiring matching contact information for cancellation actions.

### 3.4 Waiting List & Cancellation Logic

#### FR-14: Waiting List Management
- **Description:** When confirmed seats are zero but waiting list capacity remains, the system shall allow passengers to book under `WAITING_LIST` status, assigning sequential queue positions (`WL-1`, `WL-2`, etc.).
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - WL queue positions are assigned in strict FIFO order based on transaction timestamp.

#### FR-15: Ticket Cancellation
- **Description:** Passengers holding confirmed or waiting-list tickets shall be able to initiate ticket cancellation prior to train departure.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - Already cancelled tickets cannot be cancelled a second time (idempotent rejection).
  - Past journey tickets cannot be cancelled.

#### FR-16: Deterministic Refund Calculation
- **Description:** The system shall compute refunds according to documented demonstration rules:
  - Cancellation $> 48$ hours before departure: Full refund minus flat deduction (₹60 per passenger).
  - Cancellation between 12 and 48 hours: 75% refund (25% deduction).
  - Cancellation $< 12$ hours: 50% refund (50% deduction).
  - Cancellation of Waiting List ticket: Full refund minus clerical fee (₹30 per passenger).
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - The cancellation screen presents a clear summary: Original Fare, Cancellation Deductions, and Net Refund Amount before final confirmation.

#### FR-17: Automatic Waiting List Promotion
- **Description:** When a confirmed ticket is cancelled, the system shall automatically promote the first passenger in the waiting list (`WL-1`) to `CONFIRMED`, assign the freed seat, decrement subsequent waiting list numbers, and record an audit log.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - If a confirmed booking for Seat `S1-4` is cancelled, Passenger at `WL-1` is immediately updated to `CNF` with Seat `S1-4`, and Passenger at `WL-2` advances to `WL-1`.

### 3.5 Administrative & System Functions

#### FR-18: Protected Administrative Management
- **Description:** The system shall provide an administrative dashboard protected by HTTP authentication headers for managing trains, schedules, base fares, and seat quotas.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - Accessing administrative endpoints without valid admin credentials returns HTTP 401 Unauthorized.
  - Admin can update seat quota or train schedule, which takes effect immediately on subsequent passenger searches.

#### FR-19: Audit Logging
- **Description:** The system shall record non-sensitive audit events for all critical state changes: `BOOKING_CREATED`, `PAYMENT_PROCESSED`, `TICKET_CANCELLED`, `WL_PROMOTED`, and `ADMIN_MODIFIED`.
- **Priority:** Medium (Should Have).
- **Acceptance Criteria:**
  - Audit records capture timestamp, event type, booking reference, and client IP without recording sensitive credentials.

#### FR-20: Robust Error Handling and Graceful Degradation
- **Description:** The system shall safely handle invalid payload inputs, database locked states, network interruptions, and malformed requests, returning clean HTTP status codes and user-friendly error messages.
- **Priority:** High (Must Have).
- **Acceptance Criteria:**
  - Unhandled exceptions return HTTP 500 with a sanitized JSON payload: `{ "error": "Internal Server Error", "message": "An unexpected error occurred. Please try again." }`.

## 4. Interface Requirements

### 4.1 User Interfaces
- **Responsive Layout:** Dynamic layout adapting to mobile ($< 640$ px), tablet ($640-1024$ px), and desktop ($> 1024$ px) viewports.
- **Design System:** Tailored slate/blue palette with high contrast, semantic color badges (Green for `AVAILABLE`/`CONFIRMED`, Amber for `WL`, Red for `CANCELLED`/`FAILED`).
- **Interactive Feedback:** Visual spin indicators during API queries, modal confirmations for irreversible actions (cancellation), and toast notifications for success/error alerts.

### 4.2 Hardware Interfaces
- Standard client machine with minimum 2 GB RAM, display resolution $\ge 1280 \times 720$, and standard input devices (keyboard and mouse/touchscreen).

### 4.3 Software Interfaces
- **Express Backend $\leftrightarrow$ SQLite Engine:** Direct database connection utilizing synchronous transaction boundaries (`BEGIN IMMEDIATE`).
- **React Frontend $\leftrightarrow$ Express Backend:** Asynchronous REST API utilizing JSON over HTTP (Port 5000 server, Port 5173 client in development).

### 4.4 Communication Interfaces
- RESTful HTTP/1.1 protocols transmitting UTF-8 encoded `application/json` request and response payloads.

## 5. Performance Requirements

All performance metrics are specified as testable acceptance thresholds for the local demonstration environment:
1. **Train Search Latency:** Backend query and response time shall be $< 300$ ms for routes with up to 20 stations.
2. **Booking Transaction Latency:** End-to-end atomic reservation and PNR issuance shall complete in $< 500$ ms.
3. **Frontend Initial Load Time:** First Contentful Paint (FCP) of the React SPA shall be $< 1.5$ seconds under local server execution.
4. **Concurrent Booking Integrity:** System shall maintain transaction serializability under at least 20 simultaneous booking attempts without deadlock or data corruption.

## 6. Design Constraints

1. **Monorepo Architecture:** Frontend, backend, database initialization, and documentation must reside in a unified, version-controlled workspace.
2. **Platform Portability:** System must execute seamlessly on Windows, Linux, and macOS without requiring platform-specific binary compilation tools.
3. **Zero Real Credentials:** The application must never solicit or store real bank credentials, credit card CVVs, or government identification tokens.
4. **Zero Overbooking Invariant:** $\sum \text{Allocated Seats} \le \text{Total Class Capacity}$ must hold true as an unbreakable database invariant at all times.

## 7. Non-Functional Quality Attributes

### 7.1 Reliability & Data Integrity (NFR-01)
- The system shall preserve ACID properties. If any step of seat allocation, passenger record creation, or payment logging fails, the entire transaction is rolled back.
- Mean Time Between Failures (MTBF) shall exceed demonstration testing bounds with zero database corruption events.

### 7.2 Usability & Accessibility (NFR-02)
- Form inputs shall feature intuitive labels, keyboard tab navigation, and clear validation feedback conforming to WCAG 2.1 Level AA contrast guidelines.
- The train search interface shall feature a one-click station swap action.

### 7.3 Security & Privacy (NFR-03)
- Administrative routes shall require authorization tokens.
- Passenger search history shall be scoped to matching contact credentials; indiscriminate public listing of all passenger bookings is forbidden.
- Simulated payment tokens are short-lived and non-reusable.

### 7.4 Maintainability & Modularity (NFR-04)
- Codebase shall adhere to SOLID principles with strict separation between Controllers, Services, and Repositories.
- Cyclomatic complexity of core business methods shall not exceed 10.

### 7.5 Portability (NFR-05)
- Application configuration shall be externalized via `.env` files.
- The persistent SQLite database shall be stored in a portable `.db` file within the repository.

### 7.6 Testability (NFR-06)
- 100% of functional requirements (FR-01 through FR-20) shall have automated unit or integration tests that can be executed via a single `npm test` command.
